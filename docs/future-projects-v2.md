# 今後の開発プロジェクト提案 v2 — 「新しみ」重視版

作成日: 2026-08-10
対象: ta-yan.ai / YANAi Taketo の次の一手

---

## この文書について

[v1（`future-projects.md`）](./future-projects.md) は「既存資産の横展開」に寄りすぎていた。
Yagura のエージェント、証明書棚卸し、合併データのライブラリ化——どれも堅いが、
どれも「すでに作ったものの2周目」であって新しみがない。

そこで今回は**発想の方法自体を変えた**。以下の6つの異なるレンズで並行にブレインストームし、
出てきた案を別の検証者が Web 調査で「それ、本当に存在しないのか」と潰しにかかる、という手順を取った。

| レンズ | 狙い |
|--------|------|
| 新技術フロンティア | WebGPU / WASM / Web Serial / local-first など未着手の技術を主役に |
| AI・LLM ネイティブ | ChatGPT の薄い皮ではない、LLM でなければ成立しないもの |
| ハードウェア・電波・物理世界 | ソフトだけで完結しない、実物に接続するもの |
| 日本の制度・法令・公共データ | 合併マップの続編ではない、全く別の未開拓領域 |
| 地方・山口・現場の困りごと | モットーの原点。都市部のIT企業では発想されないもの |
| 逆張り・非自明な転用 | 物理シミュ・信号処理の力を想定外のドメインへ |

**結果: 30 案を発想 → 既存性検証で 5 案が即死 → 統合・重複排除して 8 案。**

検証は容赦なくやらせた。「調べた限り存在しない」と書くなら実際の検索クエリを記せ、
既存品があるならその最終更新日・価格・日本語対応まで確認せよ、という条件を付けた結果、
**発想側が主張した新規性の根拠が崩れて死んだ案が複数出た**。この失敗例も後半に載せている。
むしろこちらのほうが今後の企画判断に効くかもしれない。

> ⚠️ 本文中の競合プロダクトの価格・更新日・機能は、いずれも調査時点（2026-08）の Web 調査に基づく。
> 着手を決める前には必ず自分の目で再確認してほしい。

## 1. 見えてきた4つのテーマ

### テーマ1: 国が整備した無償の3D・標高データと、誰も繋いでいない配線をつなぐ

PLATEAU（全国の3D都市モデル）と国土地理院の標高タイル（DEM5A/5B/10B、**出典明示のみで申請不要**）は
世界的にも稀な公共資産でありながら、GNSS の可視予測にも電波伝搬にも天空率にも接続されていない。

- 海外 OSS（Meshtastic Site Planner）は SRTM 90m/30m を使うため**日本の細い尾根と谷を潰してしまう**
- 学術側（UCL の shadow matching、Skymask Matching）は**論文のまま一般に開かれていない**

この断絶は10年以上埋まっておらず、しかも埋めるのに必要なのは新発明ではなく「繋ぐ」作業。
合併マップの MapLibre とクレーンsimの数値計算が**同時に効く唯一の領域**でもある。

### テーマ2: 一次資料を「読み物」ではなく「実行可能なデータ」に変える

郵政省告示第405号（EWSツール）と総務省・国交省の合併情報（合併マップ）で、
一次資料を読んで構造化する型はすでに実証済み。この型がまだ当たっていない一次資料が大量に残っている。

消防法別表第一、協会けんぽの都道府県別料率30年分、建築基準法の改正附則と経過措置——
いずれも**解説記事は飽和しているのに機械可読な実装が存在しない**。
海外 OSS も大手 SaaS も構造的に参入できず、一度作れば長く参照され続ける。

### テーマ3: 画面の外にある実物に計算を当てる

動いているレガシー業務アプリ、現場のシリアル機器、ホッパーの中の粉、介助者の腰。
いずれもソフトウェアが届いていない対象で、そこに低レイヤ（C#/UI Automation）・
力学（RK4、剛体）・ネットワーク（WireGuard/Tailscale 由来の NAT 越え理解）の土地勘が効く。

純粋な Web アプリ競争では後発が不利だが、**「実物の側の知識」が要求される瞬間に競合は一気に減る**。

### テーマ4: 新規性の根拠を「既存が無い」ではなく「自分にしか集められないデータ」に置く

今回の検証で最も多くの案を殺したのは、まさに「調べた限り無い」という主張の崩壊だった。
逆に生き残った案は例外なく、**彼の実務経験・彼の設備（Proxmox）・彼の立場（winget-pkgs の fork）でしか
集まらないデータ**を中核に持っていた。

> 今後の企画判断の第一問は「これは無いか」ではなく「**これは自分にしか集められないか**」であるべき。

## 2. 提案 8 件

### 🥇 1位｜天窓（TENMADO）— 見上げた空の遮蔽エンジン

> 地図で1点を指すと、その地点から見上げた全方位のスカイラインが国土地理院の標高タイルと PLATEAU から
> 立ち上がり、「衛星が見えるか」「電波が通るか」を同じエンジンで答える。

**スコア**: 新規性 4/5 ／ 実現性 4/5 ／ 需要 4/5 ／ 適合 5/5
**工数**: MVP 1〜1.5か月、電波モードまで含めて3か月

**課題**
ドローン測量・RTK測量の担当者が現地に着いてから「ビルの谷間で Fix しない」と気づいて出直す。
もう一方では、920MHz帯 LoRa/Wi-SUN で獣害センサや水位計を山に置く農家と自治体職員、
山間部の別棟へ Wi-Fi を飛ばしたい人、アマチュア無線家のロケハンが
「設置してから届かないと分かる」を繰り返している。
どちらも本質は同じ問いで、**「この地点から空はどこまで開いているか」を誰も安く正確に答えられていない**。

**なぜ新しいか（調査で判明した事実）**

- *GNSS側*: Trimble GNSS Planning Online は査読論文（Surveying 2024）が指摘する通り
  「受信点周辺の建物や山といった個別事情は通常考慮されない」設計で、現行版は最低仰角の入力しか持たない。
  内閣府の GNSS View（2014年公開、無料）も天空が全開の前提。
  逆に3D建物を使う手法（UCL Groves らの shadow matching、Skymask Matching、Inha の IGSS）は
  **全て論文・研究コードで一般に開かれていない**。この断絶が10年以上埋まっていない。
- *電波側*: Meshtastic Site Planner（106★、SPLAT! の ITM を WASM 化しブラウザ完結）が強力だが、
  DEM が AWS の SRTM 90m（高解像でも30m・30km制限）で日本の地形を再現できない。
  国内は Android アプリ「電波伝搬シミュレーション」が2015年5月で更新停止、商用は
  構造計画研究所 RapLab / Infovista Planet / アジア航測 Denpa Pro のみ。

→ **残っている空白は明確に2つだけ**: (a) 日本の高解像度 DEM と PLATEAU を使うこと、
(b) 日本の制度（ARIB STD-T108 の20mW/250mW、W56 の DFS 屋外制限、QZSS）を UI に内蔵すること。
海外 OSS が構造的に持てない差はここにしかない。

**技術**
国土地理院の標高タイル（`cyberjapandata.gsi.go.jp/xyz/dem/`、PNG数値タイル、出典明示のみで申請不要）
＋ PLATEAU CityGML → 3D Tiles。核は**「方位角ごとの最大仰角プロファイル（スカイライン）」への前処理**で、
これは shadow matching の文献で building boundary method として確立済みの標準手法。
この1次元配列さえ作れば、24時間×全衛星の可視判定もフレネルゾーンのクリアランス判定も一瞬で終わる。
衛星軌道は SGP4（TLE は CelesTrak から日次スナップショット）、描画は MapLibre GL JS ＋ Three.js。

新しいのは軌道力学（ECI/ECEF/ENU 変換）と CityGML 前処理だが、RK4 と座標変換を書ける人間には地続き。

**MVP**
PLATEAU 整備済みの数都市に限定、単一地点、GPS+QZSS のみ。
日時指定で24時間スカイプロット＋可視衛星数と PDOP の推移グラフ＋
3Dで衛星から地上点への光線が建物に遮られる様子を表示。電波モードは第2段。

**リスク**
LOD1 は建物を箱で近似するため実際の遮蔽と乖離する。街路樹・電柱・仮設物はモデルに存在しない。
「測量計画の参考であり実測を代替しない」の明示が必須。
電波モードでは「本ツールの出力は電波法上の適合判定・免許申請の根拠にはならない」を明記し、
免許不要局モードでは**空中線電力上限を UI 側でハードに強制**して制度を超える入力を受け付けない設計にする。

**Wow**
3Dのビル街の谷間に、衛星から降りてくる光線が建物に遮られて赤く消える。
時刻スライダーを動かすと空を横切る軌跡と PDOP のグラフが連動して踊る。
電波モードでは地形断面が立ち上がり「この尾根で切れている。**あと3.2m上げれば60%クリアランスを満たす**」が数秒で出る。

**なぜ1位か**
4項目すべてが4以上で、しかも空白が「誰も思いつかなかった」ではなく
「商用は3D遮蔽を持たず、3D遮蔽を持つものは論文のまま」という**構造的なもの**なので、
後から誰かに一瞬で埋められる性質ではない。
地理院が標高を PNG タイルで配信済みのため、当初最大の難所とされたデータパイプラインが丸ごと消えている。
ここで作るスカイライン計算エンジンは、そのまま8位の天空率（SORAMI）に転用できる。

### 🥈 2位｜KOSHI — 介助力学ラボ

> 移乗介助で介助者の腰にかかる力を人体モデルで数値化する。
> 「膝を曲げろ、腰を近づけろ」を、初めて数字で説明する。

**スコア**: 新規性 4/5 ／ 実現性 4/5 ／ 需要 4/5 ／ 適合 4/5
**工数**: 2〜3か月

**課題**
介護職・看護師の腰痛は離職理由の上位を占めるのに、指導は「ボディメカニクス8原則」という
言葉と写真だけで、**なぜ効くのか・どれくらい効くのかが定量化されていないため現場で守られない**。
福祉用具やリフトの導入を稟議で通したい現場責任者も、数字がないので説得できない。

**なぜ新しいか（調査で判明した事実）**
英語圏には研究があり、日本語圏には啓発記事しかなく、**その中間の「誰でも触れる対話型の道具」が完全に欠けている**。

- 学術側: Banks et al. 2023「Applying Forces Measured at the Hands to Estimate L5/S1 Compression
  During Manual Patient Bed-to-Wheelchair Transfers」、MDPI Applied Sciences 2021 など、
  まさにベッド-車椅子間移乗の L5/S1 圧縮力をパラメータ別に出した論文が既にあるが、
  いずれも**一般公開の対話型ツールになっていない**
- 人間工学ツール: 3DSSPP（ミシガン大）は2020年10月から VelocityEHS|Humantech の独占ライセンスで商用化。
  しかも工場での荷物の持ち上げが前提で、「相手が人間で、不随意に動き、抱えどころが限られる」介護特有の状況を扱わない
- 日本語圏: 三幸福祉カレッジ・湘南国際アカデミー等の解説記事とイラストのみ。力学モデルを持つシミュレーターは1件も存在しない
- GitHub 検索「biomechanics lifting L5/S1 lumbar load web simulator ergonomics interactive」は**総ヒット0件**

**技術**
JavaScript + Three.js。逆動力学（準静的つり合い）によるリンクセグメントモデルの関節モーメント計算。
人体各部の質量比は Winter の人体計測データや産総研の公開データベース。
閾値の根拠には**厚生労働省「職場における腰痛予防対策指針」**を使い、自作の基準を作らず一次資料に乗る
（EWSツール・合併マップと同じ作法）。

**MVP**
「ベッドから車椅子への移乗」1シーンのみ。介助者の身長・体重、被介助者の体重、ベッド高さ、
両足の開き、膝の曲げ角、体幹前傾角の6スライダー → L5/S1 にかかるモーメントの数値表示と
推奨閾値超過の色分け。3Dは簡素な棒人間で十分。

**リスク**
労働安全・医療に隣接するため、断定的な安全判定は避け、
**「絶対値の予測器ではなく、条件を変えたときの相対比較の道具」**と位置づけを最初から明示する。
介護現場を「やり方が悪い」と責める調子になると強く反発されるので、環境と用具の改善を促すトーンで作る。

**Wow**
「ベッドの高さを5cm変えるだけで腰の負担がこれだけ違う」がグラフでリアルタイムに動く。
介護・看護の教育現場は情報共有が速く SNS 拡散力が非常に強い層で、当事者数も桁違いに多い。
**「用具導入の稟議に使える数字」という業務上の実利**があるため、一過性のバズで終わらない可能性がある。

**なぜ2位か**
検証で最も空白がきれいに確認できた案（GitHub 0件、英語圏は論文のみ、日本語圏は啓発記事のみ）。
既存7プロダクトのどれとも見た目が重ならず「新しみ」の要求を素直に満たし、
モットー「困っている人の『それ欲しかった』を作りたい」に最も直球で当たる。
1位にしなかった唯一の理由は、**介護現場に一度触ってもらえるかが品質と説得力を分ける**のに、
その接点が現時点で不確実なこと。逆に言えば接点が確保できるなら1位と入れ替えてよい。

### 🥉 3位｜Utsushi（写し）— 動いている業務アプリから仕様書を起こすエージェント

> ソースコードが失われた業務アプリを実際に起動させ、画面を這って回って項目定義書と画面遷移図を復元する。

**スコア**: 新規性 4/5 ／ 実現性 3/5 ／ 需要 4/5 ／ 適合 5/5
**工数**: MVP 1か月弱、実用水準まで3〜4か月

**課題**
日本中の中小企業に「動いてはいるがソースも設計書も作った人もいない」Windows業務アプリ
（VB6/WinForms/Delphi製）が大量に残っている。刷新しようにも、
まず**「今どういう仕様なのか」が誰にも分からず、そこで止まる**。

入力は実行中のそのアプリだけ。出力は画面ごとの項目定義書（ラベル、コントロール種別、桁数、
必須/任意、選択肢、入力制限）、画面遷移図（Mermaid）、移行後の受け入れテスト項目の雛形。

**なぜ新しいか（調査で判明した事実）**
最も近い既存品は**「画面要素解析くん」**（nodakoubou.net、2026年5月 v1.0.0、個人利用は無料・法人は課金）。
実行中の Windows アプリの UI 要素を AutomationId・座標・テキスト・クラス名・コントロール種別ごと
一括取得し CSV/JSON/Excel に書き出す。ただし——

> **AI を一切使わず機械的なダンプに留まり、画面定義書・画面遷移図・テスト項目の生成は行わないと公式に明記されている。**

つまり本案の価値の芯（`txtCd1` が得意先コードで6桁で F4 検索が開く、という業務的な意味づけ）の
**直前で止まっている**。これは推測ではなく確認済みの空白であり、
しかもそのツールが有償で成立している事実が**需要の存在を3か月前のデータで裏付けている**。

AI リバースエンジニアリングは NTTデータ・東芝・CodeAGI・CodeReverse AI・VSSD・Reversa と飽和しているが、
**全て「ソースコードを読む」前提**。ソース無しで GUI を観測する手法は
Thoughtworks の blackbox reverse engineering（Web アプリ対象のコンサル事例）と
InfraMind（arXiv 2509.13704、論文）に留まり、Windows ネイティブ・製品としては存在しない。
配管側は CursorTouch/Windows-MCP（MIT、UI Automation ベース）が既製化されており、これは脅威ではなく**追い風**。

**技術**
C#/.NET で UI Automation（取れない自作描画コントロール用に MSAA とスクリーンショットのフォールバック）。
取得したツリーとスクリーンショットをマルチモーダル LLM に渡して意味づけ。安全のため2モード構成:

1. **読み取り専用探索モード** — タブ移動・フォーカス走査・メニュー展開のみで、ボタンは押さない
2. **同伴モード** — 人間が普段どおり操作するのを横で記録し、操作列と画面遷移を学習

新しいのはエージェント設計（探索の計画と停止条件）とマルチモーダル LLM による UI 理解で、
**C#/WinForms/業務システムという最も得意な土俵の上に載る**。

**リスク**
VB6 の OCX や独自描画グリッドは UI Automation に応答せず VLM 補完に頼るため精度が読めない
→ **「UIAで取れた項目」と「画像から推測した項目」を出力上で明確に区別**し、後者に確信度を付ける。
他社製ソフトの解析はライセンス条項（リバースエンジニアリング禁止）に触れうるので、
対象を自社保有・自社運用アプリに限定する旨を UI と README の両方に明示し、
**公開デモは必ず自作サンプルアプリで行う**。本番DBに接続したアプリでの探索を止める UI 設計も要る。

**Wow**
「誰も仕様を知らないアプリを起動して放置したら、翌朝に仕様書ができていた」という絵。
日本の受託開発・情シス界隈が全員痛みを持っている問題で、
しかも大企業向けの高額サービスしか存在しない領域に個人開発のツールが刺さる構図。

**なぜ3位か**
検証で唯一、**既存品の存在が新規性を否定するどころか補強した案**。
「需要は確認済み・そのすぐ手前で誰も止まっている」という最も安全な形の空白で、
C#/WinForms/業務システム/SQL Server という経歴がそのまま製品の信頼性の担保になる（適合 5/5）。
1〜2位に置かなかったのは、痛みを持つ層のSNS拡散力がやや弱く、話題化が業界メディア経由に依存するため。

### 4位｜危険物そろばん（Kikenban）

> SDS の PDF を放り込むだけで、消防法の類・品名と指定数量を根拠行つきで引き当て、
> 置き場ごとの倍数を積み上げる完全オフラインの Windows アプリ。

**スコア**: 新規性 4/5 ／ 実現性 3/5 ／ 需要 4/5 ／ 適合 5/5 ｜ **工数**: 2〜3か月

**課題**
山口の中小の塗装屋・印刷屋・造船の下請・農協の給油所・クリーニング店には、
一斗缶やドラムでシンナー、洗浄剤、切削油、アルコールが並ぶ。
消防法では指定数量の1/5を超えると少量危険物の届出、1倍を超えると許可施設になるが、
**「どの薬品が第4類第何石油類で、水溶性か否か」を SDS から判定し置き場ごとに倍数を足し上げる作業は誰もやっていない**。
消防の立入検査で指摘されて慌てるのが常。

**なぜ新しいか（調査で判明した事実）**
既存が**「無料の電卓」と「月額5万円の企業向けSaaS」にきれいに二分され、その間が完全に空いている**。

- *無料側*: 三原市「危険物倍数計算ツール」、川崎市「危険物貯蔵・取り扱い数量算定計算書」、東京消防庁の届出書入力アプリ
  → いずれも**「第4類第何石油類か、水溶性か」を人が既に知っている前提**の電卓と様式
- *有償側*: ケミカン（PDF アップロードで99%精度のデータ化、累計2,000社、**月額50,000円〜・税別・年間契約必須**）、
  Dr.EHS Chemical、SDS Meister、ESH Clouds-Chemicals
  → 全てクラウド前提・高額・大企業向けで、**SDS を社外に出す構成**

SDS の PDF から引火点・沸点・水溶性の記述を読んで消防法別表第一の品名と指定数量を
根拠行つきで引き当てるものは、日英いずれの検索でも発見できなかった。
**SDS が社外秘であるという業務上の制約が、クラウドSaaSを原理的に排除して彼のデスクトップアプリを正解にしている。**

**技術**
PDF のテキスト/表抽出、JIS Z 7253 の16項目構造に沿ったセクション分割、
「引火点 21℃(密閉式)」のような日本語数値表現の抽出、消防法別表第一のルールエンジン化。
UI は WPF で主戦場だが、**文書構造解析・日本語の数値単位パース・法令のルールエンジン設計は
7プロダクトのどれとも重ならない新領域**。既定はルールベースで根拠を追える形にし、必要ならローカルLLMを補助に。
winget 配信経路を既に持っているのが効く。

**リスク**
誤った倍数のまま無許可貯蔵になれば消防法違反で刑事罰もありうる。
**「最終判断は所轄消防署に確認」を出力帳票にも印字**する。
SDS の著作権と機密性はクラウドに一切送らない設計で回避。
市町村火災予防条例は自治体ごとに異なるため、MVPでは消防法本体（第4類・指定数量）のみに範囲を明示的に限定する。

**注意点**: 「全自動を狙わない」ことが完成の鍵。**どの行をどう読んだかを必ず画面に出し、
人が1クリックで直せる半自動**に割り切ること。刑事罰のありうる領域では、
根拠行を必ず見せる仕様がリスク対策と製品価値を同時に満たす。

### 5位｜Kona（粉）— ブラウザで動く粉体シミュレーター

> 数万〜数十万粒子の離散要素法をブラウザで回し、
> ホッパーのブリッジやシュートの詰まりが起きる瞬間を目の前で再現する。

**スコア**: 新規性 4/5 ／ 実現性 2/5 ／ 需要 4/5 ／ 適合 4/5
**工数**: 2D版で1.5〜2か月、WebGPU化・3D化は +3か月以上

**課題**
粉体を扱う工場（食品、樹脂、セメント、肥料、金属粉、飼料）では、
ホッパー閉塞・偏析・シュート摩耗が慢性的な悩みで、出口径や傾斜角は今も経験と勘で決まっている。
DEM で検討したくても商用ソフトは数百万円クラスで、
設計者が**「ちょっと角度を変えたらどうなるか」を試す道具が存在しない**。

**なぜ新しいか（調査で判明した事実）**
商用は Granuleworks（構造計画研究所／Prometech）、iGRAF、Simcenter EDEM、COMSOL Granular Flow Module など。
無償OSSは LIGGGHTS、YADE、MFiX、MercuryDPM、Chrono::GPU、MUSEN など数多いが、
**全てデスクトップ／主にLinux／Python・入力スクリプト駆動**で、設計者が試す道具ではない。

WebGPU の粒子デモ（piellardj/particles-webgpu、WebGPU Samples、lisyarus の Particle Life 等）は
いずれも見栄え重視か SPH/分子動力学で、
**接触力学・摩擦・回転自由度を持つ本物の DEM を産業形状に当てた公開Webアプリは発見できなかった**。

**技術**
**第一版は完全2D・粒子1〜2万個・円錐ホッパー固定形状・球粒子単分散・WASM+SIMD の CPU 実装で成立させる**
（2Dなら近傍探索が単純な格子で済み、GPU並列アルゴリズムの学習を後回しにできる）。
ばね-ダッシュポット接触モデル、転がり摩擦、時間積分。
第二版以降で WebGPU/WGSL の計算シェーダ（空間ハッシュ、GPU上のカウンティングソートとプレフィックスサム）へ移行。

**リスク**
定量精度は保証できない。**「傾向を見るための検討・教育用であり設計根拠に用いないこと」を明示**。
接触剛性に対して時間刻みが大きいと粒子が吹き飛ぶため、剛性を落として現実的な dt に合わせる
工学的な妥協が必要（商用ソフトも同じことをしている）。
商用ソフトのモデル式を流用せず公開文献の Hertz-Mindlin 等に基づくこと。

**Wow — 全案中で最も強い**
ホッパーの出口径をスライダーで少しずつ縮めていくと、**ある値で突然アーチが組まれて流れがぴたりと止まる**。
粉体工学の教科書に載っている現象を、インストールなしで誰でも手元で再現できる。
産業技術者と CG・WebGPU 界隈の両方に同時に刺さる題材は極めて珍しく、
天井クレーンシミュレーターの実績があるので「この人が作るなら物理はちゃんとしている」という信頼も既にある。

**なぜ5位か**
「見た人が面白いと反応する度合い」は全案中で最高。実現性2という最大の弱点は、
**2D・CPU・1万粒子まで落とせば必ず着地する**という明確な退避路があり、
しかもブリッジ発生という見せ場は2D・1万個で完全に成立する。
ただし「WebGPUで3D数十万粒子」を最初から目指すと確実に沼る。**時間に余裕ができたときの本命**。

### 6位｜時法（じほう）— 時点を引数にする日本の制度データ

> 「2019年6月時点の東京都・協会けんぽ・介護保険第2号」で正しく引ける、日本で唯一の機械可読な制度の通史。
> 制度改正が git diff で見える。

**スコア**: 新規性 4/5 ／ 実現性 4/5 ／ 需要 4/5 ／ 適合 5/5
**工数**: 料率暦 2か月、既存不適格タイムライン +3か月

**課題**
給与の遡及訂正、算定基礎届のやり直し、未加入期間の遡及加入、退職者の再計算、未払い賃金の算定——
いずれも「過去のあの時点の料率」が必要になるのに、協会けんぽの都道府県別健康保険料率、介護保険料率、
雇用保険料率（年度途中改定あり）、労災保険率、最低賃金、所得税の速算表はすべてバラバラのPDFに散在し、
**実務では自作Excelを継ぎ足して運用され年度をまたぐと壊れる**。

同じ構造の問題が建築側にもある（中古ビルの購入・用途変更で「いつどの規定が変わり、どんな経過措置が付いたか」）。
両者は主題が違うだけで、必要なものは同一——**「規定 × 施行日 × 経過措置 × 適用トリガー」を日付で引ける機械可読データ**。

**なぜ新しいか（調査で判明した事実）**
日本で Rules as Code を最も真面目にやっている **OpenFisca-Japan**（GitHub 39★）のリポジトリを実際に開いたところ:

> `openfisca_japan/parameters/社会保険料/健康保険料率.yaml` は
> **`2000-01-01: value: 0.1` の全国一律10%固定値ただ1点**。介護保険料率.yaml も `2015-01-01: 0.016` の1点のみ。

つまり**日本の制度をコード化するプロジェクトですら料率の通史を持てていない**。
人間が読む推移表は存在する（社労士Tools が2011〜2026年度・47都道府県分、開東社会保険労務事務所 が雇用保険料率）が、
CSV/JSON配布なし・出典URLが値ごとに紐づいていない・系統ごとにサイトがバラバラ・ライブラリとして配布されていない。
協会けんぽ公式は令和3年度以降しか掲載していない。

さらに **e-Gov 法令API Version 2 が2025年3月14日にリリースされ「特定時点の検索とその時点の条文取得」に対応**した。
条文へのディープリンクを持つ実装が**今年やっと技術的に成立するようになったばかり**である。

**技術**
値ごとに有効期間（from/to）と出典URLを持つ **bitemporal**（適用期間と公表時点の二軸）データモデル。
GitHub Actions で公式サイトを定期クロールして差分を検知し更新PRを自動生成
（robots.txt とアクセス頻度に配慮、PDFは再配布せずリンクに留める）。
配布は npm、NuGet、単一JSONのCDN、そして検索UIのWeb。
**C# と JavaScript の両方でライブラリを出せるのは稀な強み**で、給与ソフトを作る業務システム屋にそのまま届く。

**MVP**
第一弾『料率暦』単体で完結させて公開する——健康保険（協会けんぽ都道府県別）・介護・厚生年金・
雇用保険・最低賃金の5系統、2010年度以降。JSONデータセット、JS版ライブラリ、時点指定で引く簡易Web UI。

**リスク**
「データセットであり税務・労務・建築の助言ではない」と明記し、
**公式の保険料額表と突き合わせた検算用テストベクタを同梱**して転記ミスを機械的に検出できるようにする。
改定の適用タイミングの罠（健保は3月分から適用・4月納付、雇用保険は年度途中改定の年がある）を
規定ごとにデータモデルで表現できるかが価値の分かれ目。
「出典URLのない項目は公開しない」を厳格に適用すると年表の前半が空になるため、
**出典の種別（一次/二次）をデータに持たせて表示で区別する設計**を最初から入れること。

**Wow**
料率30年分を折れ線グラフで並べると「**手取りが減った理由**」が一枚の絵になる。
建築側では「1971年（十勝沖地震後）、1981年（新耐震）、2003年（シックハウス）、2006年（アスベスト）」という断層を、
それぞれどの事故・災害の後に生まれたかと併記することで、**法が事故のあとに厚くなってきた歴史**という物語が立ち上がる。

**なぜ6位か**
**スコア合計は全案中で最も高く、最も確実に完成し、最も長く価値が残る（AdSense との相性も最良）**。
それでも6位に置いたのは、今回の依頼の核心が「見た人が面白いと反応する新しみ」であり、
この案の本質が地味なデータ整備だから。
トップページを「日本の社会保険料30年史」のビジュアライゼーションにして
JSON とライブラリをその裏に置く構成なら要求を満たせる。

> 💡 公開直後から実利用者を得る近道として、**OpenFisca-Japan の空の YAML へ履歴つきデータを PR で還流させる**ことを強く勧める。

### 7位｜Tachiai（立会）

> 現場のUSBシリアル機器を、ブラウザのタブごと遠隔のベテランに貸す。
> サーバもVPNもインストールも要らず、URLと招待コードだけで実機がつながる。

**スコア**: 新規性 4/5 ／ 実現性 3/5 ／ 需要 3/5 ／ 適合 4/5 ｜ **工数**: 3週間程度

**課題**
設備がトラブったとき現場に行くのは若手、機器のコマンドを知っているのはベテラン、という構図。
今は電話で「今なにが出てる？」「HEXで読み上げて」をやっている。
顧客ネットワークにVPNを張る・リモートデスクトップを入れるのは情シス承認に数週間かかり、
産業用リモートアクセス装置は機器ごとに高額。

現場側が Chrome/Edge で URL を開き USB-シリアル変換ポートを選んで招待コードを読み上げ、
遠隔側が同じ URL にそのコードを入れる、それだけ。

**なぜ新しいか（調査で判明した事実）**
COMポートをネットワーク共有する製品は多数あるが、**全て Windows に仮想COMドライバかサービスを導入する前提**
（HHD Remote Serial Ports、Eltima Serial to Ethernet Connector、Free Com Port Redirector、
papnkukn/remote-serial-port-server、ハード側は StarTech NETRS2321E 等）。
**客先PCに何も入れられないという最大の障壁を、どれも越えられていない。**

ブラウザ側の Web Serial 系（rafaelaroca/web-serial-terminal、sbooeshaghi/browser-serial 等）は
**全て単独デバッグ用途で遠隔共有機能なし**。
WebRTC ベースの遠隔支援（VSight Remote、RemoteCall）は対象が映像・画面であってシリアルポートではない。

**技術**
Web Serial API ＋ WebRTC DataChannel ＋ OPFS に全ログをチャンク保存。
シグナリングは Cloudflare Workers + Durable Objects の数十行で足りる（既に Cloudflare Pages を使っている延長線上）。
新しいのは Web Serial と WebRTC だが、**WireGuard / Tailscale で培った NAT 越え・経路・TURN の理解が
そのまま設計判断に効く、珍しく地の利のある新技術**。

**リスク（最重要）**
**実機に書き込みコマンドを流せてしまう＝設備事故のリスクが最大の論点**。
既定を読み取り専用にし、書き込みは現場側が明示的にトグルしている間だけ許可、全操作を記録。

そして最大の設計上の落とし穴——
**「VPNを張る承認が下りない」現場は、同じ理由で STUN/TURN への任意アウトバウンドや P2P 通信も止められている確率が高い。**
「同一LAN内で、事務所の自席PCから現場の実機シリアルにブラウザだけで入る」を第一の売り文句にし、
インターネット越しP2Pは副次機能に降格したほうが、承認が通る現場が増えて実際に使われる。

**成否を分ける一点**
需要3の見立ての通り、画面共有（TeamViewer/Teams）＋手元のシリアルターミナルで用の8割は足りてしまう。
それでも勝てるのは「遠隔側が自分の手で叩ける」ことと「**立会記録が自動で残る**」ことの2点だけ。
→ **立会記録（送受信ログ＋注記＋確認欄のPDF出力）を第二段階ではなくMVPに入れること。**
日本の検収・立会いの商習慣に直結する後者が、既存のどれにも無い最大の差別化要因。

### 8位｜SORAMI — 天空率のブラウザ解析エンジン

> 数十万円の専用CADに独占されている建築基準法の「天空率」算定を、
> ブラウザだけで、形を動かしながらリアルタイムに解く。

**スコア**: 新規性 3/5 ／ 実現性 3/5 ／ 需要 4/5 ／ 適合 4/5 ｜ **工数**: 3〜4か月

**課題**
都市部の設計では道路斜線・隣地斜線・北側斜線を天空率でクリアするのが標準手法だが、
算定は専用CADに事実上独占され年数万〜数十万円かかる。
結果として小規模設計事務所・学生・不動産の事業性検討者は
企画の最初期に「この敷地に何m²載るか」を試算できない。

**なぜ新しいか（調査で判明した事実 — ただし当初の主張は一部誤りだった）**
**「ブラウザ完結のものは存在しない」は誤り**で、タスキホールディングス子会社 ZISEDAI の
「TOUCH&PLAN」（2024年2月に天空率対応）と CST「ROOK2」がクラウドで天空率込みのボリューム自動生成を提供している。
ただし両者とも法人向け有償・営業経由で、個人設計者や学生が触れる導線がない。

**最も重要な発見**: 市場リーダーの生活産業研究所が、本案の MVP に相当する
企画段階のボリュームスタディ特化製品「**天空率空間**」（2024年2月リリース）を、
**2026年8月31日でサポート終了すると告知している**。
有償プロダクトとしては2年半で畳まれたが、OSS＋AdSense なら収益モデルが違い、
「大手が撤退した直後に無料版が出る」構図は話題性として有利に働く。

**技術**
Three.js/WebGL2 + 球面解析幾何。天空率は本質的に「半球を正射影した円上での投影面積比」であり、
**1位の天窓で作るスカイライン計算と数学的に同じ土俵**にある。
建物稜線を単位球に投影して円弧多角形の面積を厳密に解く解析解を主計算に据え、
GPU の正射影オフスクリーンレンダは検算と可視化に使う二重構成。
（クレーンシミュレーターの物理エンジンは一切流用できない。あちらは数値積分、こちらは幾何と解析。）

**難所**
適合建築物の自動生成に加えて、**算定位置の配置ルール**（道路幅員の2倍かつ35m以内の区域分け、
後退距離による道路境界線のみなし移動、二方道路・屈曲道路）が単純敷地でも避けられない。
矩形敷地＋直線道路1本という縛りを守れば到達可能。

**リスク**
確認申請の正式図書として使われる誤用が最大のリスク。
「検討用であり、審査機関提出前に専用ソフトで検証すること」を明示。
審査機関ごとに算定位置の取り方などの運用差があるため断定的表現を避ける。
法令の数式・図表そのものは著作権の対象外だが、ADS 等の**出力書式（三斜求積図のレイアウト等）を模倣しない**こと。

**なぜリストに残したか**
新規性3（世界初ではなく「無料圏では初」）なので上位には置けないが——
(1) 1位の天窓と半球投影・遮蔽幾何のエンジンを共有でき、**天窓を先に作れば実質的な追加コストが下がる**、
(2) 市場リーダーが同じニッチの製品を今月末で畳むという、めったにないタイミングの物語がある、
(3) 絵としての訴求力が高く需要も明確。
**天窓を完成させた後の第2弾として最も自然な位置**にある。

## 3. 落とした案と、その教訓

検証で死んだ案のほうが学びが大きいので、6件を理由つきで残しておく。
今後の企画判断のチェックリストとして使えるはず。

### ❌ Utsushi — Oracle→PostgreSQL 移行検証ラボ
「変換して終わりで、変換先を実際に走らせて等価性を確かめるものは無い」が事実誤認。
インサイトテクノロジーの **Insight SQL Testing** が「2DBモード」で
Oracle/SQL Server/PostgreSQL/MySQL/Snowflake 間の実行可否・結果・速度の突合を商用提供済み。
変換側も ora2pg・AWS SCT・sqlglot・polyglot（Rust/WASM、33方言、ブラウザ playground 公開済み）が押さえ、
ブラウザ実行側も PGlite 公式 playground・codapi.org が既に無料。

> **教訓**: この案は「期待結果CSVを用意するには移行元Oracleで実行できる環境が要る。
> それができる現場なら本物のPostgreSQLも大抵立てられる」という論理で、
> ブラウザ完結の必然性が内側から崩れていた。
> **差別化の根拠が「既存に無い機能」ではなく「利用者の制約条件」である場合、
> その制約条件が本当に成り立つかを最初に検算せよ。**

### ❌ Doukon — 配布物の同梱漏れDLL検出
新規性の根拠が丸ごと「既存が古い」に置かれていて、それが崩れた典型例。
「Dependency Walker は2006年で止まり ApiSet を解決できない」は正しいが、**後継が2つ健在**。
hfiref0x/**WinDepends** は完全書き直しで delay-load・ApiSet コントラクト・bound import・SxS に対応し、
**リリースは2025年11月30日・12月27日と直近まで更新継続**。lucasg/Dependencies も現役。

> **教訓**: (1)「既存が古い」を新規性の根拠にする案は、**まず既存の最新リリース日を確認せよ**。
> (2) この案で本当に空いていたのは解析エンジンではなく**データ側**
> （各Windowsバージョンのクリーン環境 System32 DLL 在庫）だった。
> Proxmox で各OSを立てて棚卸しを自動化できる設備を持っているのだから、そちらに反転すれば模倣困難だった。
> **価値がツール側ではなくデータ側にあるケースを見分けること。**

### ❌ Sumikeshi — ブラウザ内日本語PIIマスキング
「ブラウザ完結・オフライン・OSSで日本語対応は見当たらない」の前半が完全に誤り。
montevive/**openai-privacy-filter** が transformers.js v4 + WebGPU・100%ローカル推論という
**ほぼ同一のアーキテクチャ**で公開済み。**LocalRedact** は WebLLM で Qwen3-4B をブラウザ内実行し、
pdf-lib で元テキストを完全除去したPDFを出力——本案が「正しい墨消し」として掲げた機能を先に実装している。
日本語特化側も Presidio + GiNZA、fuseji が先行。

> **教訓**: **「ブラウザ内でローカル推論」という差別化は2025〜2026年にかけて完全に消費済み**で、
> 構成そのものは新規性を生まない。
> 残った差分が「既存の英語ツールの日本語版」に縮退したら、それは新規性ではなく**ローカライズ**である。

### ❌ 琥珀（紙焼きアーカイバ）／ 形見箱（デジタル遺品の金庫）
「紙×暗号×長期保存」は世界的に手垢がついており、直近数か月でも新作が出続けている。
琥珀が「決定的な違い」とした冗長符号と自己記述性は za3k/**qr-backup** が両方実装済み
（dense mode で最大130KB/A4、RSで30%欠損まで復元、復元手順が人間可読でPDFに印刷される）。
容量でも Twibright Optar 200KB > qr-backup 130KB > 提案MVP 100KB で**既存より下**だった。
形見箱も **DeadSwitch**（商用）と **Rememory**（2026年2月公開のOSS、age暗号＋閾値暗号＋単一HTML復元）が先行。

> **教訓**: 海外OSSの世界では、**同じ発想の人間が必ず既にいる前提で調べるべき**。
> 特に Hacker News / Hackaday に載る種類の題材（紙にデータを印刷する、秘密分散で遺品を渡す）は、
> **思いつきやすさの分だけ先行者密度が高い**。

### ❌ Kikimimi — スマホで作る設備の異音検知AI
技術的な差分は本物なのに、それが一般に伝わらないため話題化しないという失敗パターン。
wow として掲げた「スマホをかざして3分待つだけで、その機械専用のAIができる」は
Google **Teachable Machine** の Audio Project が**2019年から無料・ブラウザ完結・コード不要**で提供しており、
公式ユースケースに machinery fault sounds が明記されている。
実質的な差は教師あり／教師なしという点で、これは意味のある差ではあるが**見た目で区別がつかない**。
加えて提案自身が最大の難所と認めた環境ノイズと再現性は、
DCASE Challenge が専用タスクを立ててなお未解決の研究課題。

> **教訓**: 差別化が「**見た目で伝わらない技術差**」しかない場合、それがどれだけ正しくても話題性には転換されない。
> そして、**提案書が自分で「最大の難所」と書いた項目が学術界の未解決問題と一致していたら、
> それは製品の中核に据えてはいけない。**

### ❌ 操法ミラー — 消防団ポンプ操法の動作解析
技術構想も新規性も良かったのに、**市場そのものが消えつつあった**という珍しい落ち方。
操法領域にソフトウェアが一切届いていないという主張は調査でも裏付けられた。
しかし三浦市が2025年度で技術大会を廃止、いわき市が団員アンケートを経て廃止、
常滑市では1分団9人の一斉退団を受けて市大会廃止・県大会辞退——
**しかも廃止理由が「練習負担」、つまりこのツールが解こうとしている問題そのもの**。

> **教訓**: **需要の存在を確認するだけでは足りず、その需要が今どちらの方向に動いているかを確認せよ。**
> なお、音声トリガによる区間切り出し＋DTWによる基準動画との時間整列というエンジン自体は筋が良く、
> 製造業の作業時間分析（既存の OTRS 等は1ライセンス数十万円）へ対象を付け替えれば生き返る可能性がある。

|----|----|------|
