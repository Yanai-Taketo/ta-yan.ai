## 2. 提案

### 提案 1｜Yagura Windows エージェント ★最優先（戦略度：高）

**課題**: Yagura は syslog サーバだが、**Windows は syslog を喋らない**。つまり Yagura の
一番の想定顧客である Windows 現場では、イベントログを syslog に変換して送る「足」がないと
Yagura 単体では価値が出せない。

**既存の選択肢とその弱み**（※要検証）

- nxlog CE — 設定ファイルが独自記法で難解、GUI なし、日本語情報が少ない
- Snare — 商用版が中心
- Windows Event Forwarding (WEF) — Windows 同士でしか完結せず、syslog に出せない

つまり「**GUI で設定できる・無料・日本語**」の Windows syslog エージェントは空白地帯。

**機能案**

- イベントログの購読（`EventLogWatcher` / `EvtSubscribe`）→ RFC 5424 / RFC 3164 で転送
- TLS 転送（Yagura 側の TLS 受信と対になる）
- フィルタ（チャンネル / レベル / イベント ID / プロバイダ）
- Windows サービス常駐 + 設定 GUI（NTPilot の UI 資産をそのまま活かせる）
- 送信先ダウン時のローカルスプールと再送
- テキストログ（IIS、アプリログ）の tail 転送

**派生プロダクト**: 同じコードベースから「**.evtx ローカルビューア**」を切り出せる。
「対象サーバがない環境でエクスポートしたログを開いて検索・CSV 出力する」という、
OraDB DUMP Viewer とまったく同じ発想の Windows ログ版。標準のイベントビューアは
他マシンの .evtx を開くと重く、フィルタも貧弱なので、需要は堅い。

- 技術: C# / .NET、`System.Diagnostics.Eventing.Reader`、Windows Service
- 工数目安: 中（2〜3 か月）
- 効果: Yagura が「サーバ単品」から「収集基盤」になる。プロダクトが実質 2 つ増える

### 提案 2｜証明書の期限棚卸しツール（仮称: Kigen）（費用対効果：高）

**課題**: 「証明書の期限切れで朝サービスが止まる」は情シスの定番事故。しかし標準の
`certlm.msc` は 1 台ずつしか見られず、複数サーバ横断の棚卸しは PowerShell の職人芸になりがち。

**なぜ今の柳井さんに向くか**: NTPilot の成功パターン（単機能・軽量・GUI・多言語・winget 配布）を
そのまま横展開できる。作るものの形が既に手の内にある。

**機能案**

- 複数ホストの証明書ストア（LocalMachine\My ほか）を横断して一覧
- IIS のバインディングに紐づく証明書を紐付けて表示
- ネットワーク越しの取得（TLS ハンドシェイクで実際に提示される証明書を見る＝エージェントレス）
- 期限までの日数でソート・色分け、CSV / Excel 出力
- しきい値超過時の通知（メール / Teams Webhook）
- AD CS 環境ならテンプレート名・発行元も表示

- 技術: C# または VB.NET / WinForms、`X509Store`、`SslStream`
- 工数目安: 小〜中（1〜2 か月）
- 差別化: 無料・日本語・GUI・エージェントレス

### 提案 3｜市区町村コード名寄せライブラリ（仮称: jp-muni）★最速で成果が出る

**着眼点**: 市区町村合併マップで **706 件の変更イベントを既に整備済み**。
つまり一番しんどいデータ整備という参入障壁を、すでに越え終わっている。
これをビジュアライズだけで終わらせず、**データ + ライブラリとして製品化**する。

**解く課題**: 「昭和・平成の合併で消えた旧市町村名を含む住所データを、現在の自治体コードに正規化する」。
これは官公庁・保険・不動産・物流・自治体系の案件で必ず出てくる実務課題で、
柳井さんの業務システム開発の土俵と完全に重なる。

**機能案**

- 旧市区町村名 / 旧 JIS コード → 現在のコードへ解決
- **時点指定**: 「2005 年 4 月 1 日時点の ◯◯郡 △△町」を解決
- 分割編入（1 つの町が複数の市に分かれたケース）を、候補列挙 + 按分情報付きで返す
- 都道府県・郡の変遷、市制/町制施行の履歴

**提供形態**

- NuGet（C#）+ npm（TypeScript）の 2 本立て
- データ本体は CC BY などで単独公開（引用されやすい形に）
- 静的 JSON API を Cloudflare Pages / Workers で提供

- 工数目安: **小**（データは既にある。API 設計と分割編入の扱いが山場）
- 効果: ポートフォリオに「OSS ライブラリ」枠が加わり、**ダウンロード数という定量実績**が付く。
  アプリと違い、他人のプロダクトに組み込まれる＝勝手に実績が伸びる資産になる

### 提案 4｜日本の警報音・信号音ラボ（EWS ツールの拡張／姉妹編）

**着眼点**: 緊急警報放送ツールで作った「Web Audio API + 一次資料調査」の型がそのまま使える。
緊急地震速報のチャイム、消防・救急のサイレン、踏切警報音、時報、津波警報など、
検索需要は大きいのに、**信号仕様を一次資料ベースで解説 + 生成 + 解析できる場所がほぼ無い**。

**機能案**

- 各信号の波形・スペクトログラム表示
- マイク入力からの識別・解析
- 根拠となる法令・告示・JIS へのリンク（EWS ツールで確立した作法をそのまま踏襲）

**設計上の注意**: 実運用中の警報系（J-ALERT の実信号など）は、**解析・解説のみに留めて生成機能は付けない**、
生成するものは音量制限と用途警告を必ず添える、といった線引きが要る。
EWS ツールで既に同種の判断をしているはずなので、その基準を明文化して横展開するのが安全。

- 技術: Web Audio API / AudioWorklet / Canvas
- 工数目安: 小〜中

### 提案 5｜玉掛け・フォークリフト シミュレーター（クレーンの物理エンジン再利用）

**着眼点**: 天井クレーン シミュレーターの「弾性ワイヤロープを連成した RK4・720 Hz」の物理モデルは、
玉掛け作業にほぼそのまま流用できる。技能講習の裾野はクレーン運転より玉掛けのほうが広く、
フォークリフトはさらに大きい（※具体的な受講者数は要確認）。

**玉掛け編の機能案**

- 玉掛け用具の選定（ワイヤ径・つり角度と張力増加係数）
- 重心位置のずれによる傾き・荷振れ
- 合図の練習、試験対策モード

**フォークリフト編の機能案**

- 荷重曲線（ロードチャート）と前後安定度
- 走行・荷役の複合操作、狭所での取り回し

- 工数目安: 中（エンジン流用で 1.5〜2 か月）
- 効果: 単発作品ではなく「産業機械シミュレーター」シリーズになる。
  3 作目以降は共通エンジンをパッケージ化して開発コストを逓減できる

### 提案 6｜ta-yan.ai 自体をプロジェクトハブ化（土台整備）

新規プロダクトではないが、**今後のすべてのプロジェクトの効果を底上げする**投資。

**現状の問題**

- `index.html` が 1,353 行の単一ファイル。プロジェクト追加のたびに手で HTML を編集しており、
  10 件を超えると保守が破綻する
- **各プロダクトの詳細ページが無い**。検索流入がトップページに集中し、
  Yagura や NTPilot 個別の SEO が育たない
- OGP 画像・`sitemap.xml`・`robots.txt`・JSON-LD が未整備
- `ads.txt`（AdSense）を置いている以上、流入を増やす投資の回収先はある

**やること**

- プロジェクト情報を `projects.json` に分離し、ビルド時に HTML 生成（Astro / 11ty / 自作 Node スクリプトのいずれか）
- `/projects/<slug>/` の詳細ページ（スクリーンショット、機能一覧、ダウンロード、更新履歴、FAQ）
- OGP 画像の自動生成
- `sitemap.xml` / `robots.txt` / JSON-LD（`SoftwareApplication`, `Person`）
- 英語版（Yagura・NTPilot は海外需要が見込める種類のツール）

- 工数目安: 小（1〜2 週間）

## 3. その他の候補（優先度は下）

- **タスクスケジューラ管理ツール** — 複数台のタスクを横断一覧・エクスポート/インポート。
  標準 GUI は複数台運用が厳しい。ただし証明書棚卸しより需要は狭い
- **共有フォルダの ACL 棚卸しツール** — 情シスの定番課題。既存は古いか有償。
  ただし権限周りは慎重な実装が要る
- **選挙区の区割り変遷マップ** — 合併マップの MapLibre 資産を再利用。
  衆院小選挙区の改定を時系列で追える既存サイトはほぼ無い
- **郵便番号・住居表示の変遷ビューア** — 同じくデータ系の横展開

### あえて避けたほうがよさそうな領域

- 汎用のメモ・タスク管理・生産性アプリ — 差別化要素が「作った人の趣味」しかなくなる
- 住所正規化そのもの — `normalize-japanese-addresses` など強い既存 OSS がある。
  提案 3 は「**合併による時系列の名寄せ**」に絞ることで正面衝突を避けている
